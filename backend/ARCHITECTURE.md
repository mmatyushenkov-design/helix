# Workout Tracker — локальная и серверная архитектура

Документ описывает целевую архитектуру приложения: Flutter-клиент, локальное
хранение, необязательный Python-бэкенд, модель данных, API и синхронизацию.

Главное решение: **приложение полностью работает без сервера**. База данных и
файлы пользователя находятся на устройстве. FastAPI нужен только для необязательной
синхронизации, резервного копирования на сервер и будущей работы нескольких
устройств. Запуск Python на телефоне не требуется.

---

## 1. Основные принципы

| Принцип | Практическое значение |
|---|---|
| Local-first | Открытие дневника, запись подхода, редактирование цикла и просмотр статистики работают без интернета |
| Локальная БД — источник истины | UI читает и изменяет локальную SQLite, а не ждёт ответа сервера |
| Файлы остаются на устройстве | Изображения, экспорт и резервные копии хранятся в локальной папке приложения |
| Сервер необязателен | Потеря соединения или отключение сервера не блокирует функции приложения |
| Канонические единицы | В БД вес хранится в кг, время в секундах, дистанция в метрах; фунты и мили — только представление |
| Стабильные идентификаторы | Все пользовательские сущности получают UUID на клиенте |
| Локализация данных | Переводы не зашиваются в названия колонок и не смешиваются с идентификаторами |
| Тонкие контроллеры | FastAPI принимает DTO, вызывает сервис и возвращает DTO; бизнес-правил в routes нет |
| Простота | Один локальный пользователь на старте, без микросервисов, обязательного аккаунта и фоновых очередей |

### 1.1 Два режима работы

**Автономный режим — режим по умолчанию:**

```text
Flutter UI
   ↓
Use cases / AppState
   ↓
Локальные репозитории и сервисы
   ├── SQLite: упражнения, циклы, дневник, шаблоны, настройки
   └── FileStorage: медиа, экспорт, резервные копии
```

**Подключённый режим — опционально:**

```text
Та же локальная SQLite
   ↓ Outbox + SyncService
FastAPI → сервисы → репозитории → SQLAlchemy → SQLite/PostgreSQL
```

Все действия сначала фиксируются локально. Синхронизация выполняется после этого
и никогда не определяет, можно ли пользователю сохранить тренировку.

## 2. Технологический стек

### 2.1 Flutter-клиент

- **Flutter / Dart** — UI и локальная бизнес-логика.
- **sqflite** — SQLite на Android/iOS.
- **sqflite_common_ffi** — SQLite на desktop и в хостовых тестах.
- **path_provider + path** — платформенные папки и безопасное построение путей.
- **uuid** — генерацию идентификаторов на устройстве.
- **flutter_localizations + ARB** — интерфейсные переводы.
- **SharedPreferences** — только небольшие технические настройки, не основная БД.
- При необходимости: **file_picker** для импорта и **share_plus** для отправки экспорта.

Текущий JSON-снапшот из этапа 7 остаётся совместимым источником для первой
миграции. Целевое хранилище — нормализованная SQLite, поскольку каталог упражнений,
мышцы, шаблоны и статистика требуют запросов и связей, а не одного большого JSON.

### 2.2 Python-бэкенд

- **Python 3.12+**, **FastAPI**, **Uvicorn**.
- **SQLAlchemy 2.0** — ORM для SQLite/PostgreSQL.
- **Pydantic v2** — DTO и валидация.
- **Alembic** — серверные миграции.
- **pytest + httpx** — тесты сервисов и API.
- Аутентификация добавляется только при включении удалённой синхронизации.

### 2.3 Платформенные различия

| Платформа | Основные данные | Файлы |
|---|---|---|
| Android/iOS | SQLite в приватной папке приложения | Application Support/Documents через `path_provider` |
| Windows/Linux/macOS | SQLite через FFI | Папка данных приложения |
| Web | IndexedDB как целевой вариант; текущий `localStorage` — временный fallback | Импорт/скачивание через браузер, прямого доступа к произвольным путям нет |

## 4. Общие правила модели данных

Все синхронизируемые сущности используют общий набор полей:

```text
id                  UUID, генерируется клиентом или сервером
owner_id            UUID?, null у встроенного общего каталога
created_at          datetime UTC
updated_at          datetime UTC
deleted_at          datetime? — мягкое удаление/tombstone
```

Даже без регистрации локальная установка получает `local_user_id`. Он нужен для
единообразия схемы, но не требует аккаунта и не отправляется без включённой синхронизации.

Дополнительные правила:

- UUID в SQLite можно хранить как `TEXT`; на PostgreSQL — как native UUID.
- Календарная дата тренировки хранится как `date`, без сдвига часового пояса.
- Технические timestamps хранятся в UTC.
- Позиции упражнений, дней и подходов — целочисленные, начиная с нуля.
- Встроенные записи каталога не удаляются пользователем; пользовательские можно архивировать.
- Названия не являются ключами и не используются для связей.

## 5. Каталог упражнений и локализация

### 5.1 `Exercise`

| Поле | Тип | Назначение |
|---|---|---|
| `id`, `owner_id`, timestamps | общие | UUID и владелец |
| `slug` | str | стабильный машинный идентификатор встроенного упражнения |

| `default_step_kg` | float? | шаг прогресса по умолчанию для весовых упражнений |

| `is_archived` | bool | скрыто из выбора без удаления истории |

Уникальность имени во всей таблице не требуется: переводы и пользовательские названия
могут совпадать. Связи выполняются по `id`.

### 5.2 `ExerciseTranslation`

| Поле | Тип | Назначение |
|---|---|---|
| `exercise_id` | FK → Exercise | |
| `language_code` | str | `ru`, `en` и следующие языки |
| `name` | str | локализованное название |
| `description` | str? | техника/пояснение |

Уникальная пара: `(exercise_id, language_code)`. При отсутствии языка используется

Пользовательский редактор создаёт `Exercise`, перевод названия и связи с мышцами
в одной локальной транзакции.

### 5.3 `MuscleGroup`, `Muscle`, `ExerciseMuscle`

```text
MuscleGroup
───────────
id                  UUID
code                str unique       # chest, arms, back...
position            int

Muscle
──────
id                  UUID
group_id            FK → MuscleGroup
code                str unique       # biceps, triceps, lower_back...
position            int

ExerciseMuscle
──────────────
exercise_id         FK → Exercise
muscle_id           FK → Muscle
role                enum             # primary | secondary
```

Начальные группы: грудь, руки, спина, ноги, плечи, корпус, фулбади, кардио.
Внутри групп задаются подразделы, например бицепс/трицепс/предплечье или
центр спины/широчайшие/поясница. Список хранится в данных, а не в `if` внутри UI.

Коды групп и мышц переводятся через ARB на клиенте. Если в будущем пользователи
смогут создавать собственные разделы, для них добавляется таблица переводов по
тому же принципу, что и для упражнений.

Упражнение может иметь несколько основных и вспомогательных мышц. Это необходимо
для фулбади и сложных движений.

## 6. Форматы записи и единицы измерения

### 6.1 `RecordFormat`

```text
WEIGHT_REPS       вес + повторения
WEIGHT_TIME       вес + время
TIME_REPS         время + повторения
TIME_DISTANCE     время + дистанция
```

Формат принадлежит упражнению. Редактор подхода показывает только нужные поля.

| Формат | Обязательные значения | RIR |
|---|---|---|
| `WEIGHT_REPS` | `weight_kg`, `reps` | доступен |
| `WEIGHT_TIME` | `weight_kg`, `duration_sec` | опционально |
| `TIME_REPS` | `duration_sec`, `reps` | опционально |
| `TIME_DISTANCE` | `duration_sec`, `distance_m` | не используется |

Проверка выполняется в локальном сервисе и повторяется на сервере. Дополнительно
в SQLite/PostgreSQL добавляются `CHECK`-ограничения против отрицательных и пустых
обязательных значений. Произвольный JSON для основных показателей не используется:
иначе статистика и миграции становятся ненадёжными.

### 6.2 Канонические единицы

```text
weight_kg           REAL, килограммы
duration_sec        INTEGER, секунды
distance_m          REAL, метры
```

Настройки `kg/lb` и `km/mi` влияют только на ввод и отображение. Переключение
единиц не перезаписывает историю. Конвертация находится в `core/units.py` и
`domain/services/units.dart`, округление выполняется только на границе UI.

`default_step_kg` и шаг цикла также хранятся в кг. При фунтах UI может предлагать
удобные фунтовые шаги, сохраняя их канонический эквивалент.

## 7. Циклы

### 7.1 `Cycle`

| Поле | Тип | Назначение |
|---|---|---|
| `id`, `owner_id`, timestamps | общие | |
| `exercise_id` | FK → Exercise | одно упражнение на цикл |
| `best_weight_kg` | float | лучший подход |
| `best_reps` | int | повторения лучшего подхода |
| `tm_kg` | float | расчётный разовый максимум |
| `step_kg` | float | минимальный шаг прогресса |
| `weight_offset_kg` | float | накопленная прибавка после кругов |

### 7.2 `CycleDay`

| Поле | Тип | Назначение |
|---|---|---|
| `id`, timestamps | общие | |
| `cycle_id` | FK → Cycle | |
| `position` | int | порядок, максимум 8 дней |

### 7.3 `CycleSet`

| Поле | Тип | Назначение |
|---|---|---|
| `id`, timestamps | общие | |
| `day_id` | FK → CycleDay | |
| `position` | int | порядок подхода |
| `weight_kg` | float? | точный плановый вес |
| `pct` | int? | процент от ТМ вместо точного веса |
| `reps` | int? | повторения |
| `duration_sec` | int? | резерв для других типов прогрессии |
| `distance_m` | float? | резерв для других типов прогрессии |
| `rir` | int? | запас повторений |

Для текущего силового цикла ровно одно из `weight_kg`/`pct` заполнено, а `reps`
обязательно. Точный вес не округляется при бампе. Процентный вес рассчитывается
от ТМ и округляется до шага по правилам интерфейса.

## 8. Дневник тренировок

### 8.1 `WorkoutEntry`

| Поле | Тип | Назначение |
|---|---|---|
| `id`, `owner_id`, timestamps | общие | |
| `date` | date | календарный день |
| `exercise_id` | FK → Exercise | |
| `record_format` | enum | снимок формата на момент тренировки |
| `cycle_id` | FK → Cycle? | если запись связана с циклом |
| `cycle_day` | int? | выполняемый день цикла |
| `source_template_item_id` | UUID? | источник, если добавлено из шаблона |
| `position` | int | порядок и drag & drop |
| `done` | bool | нажата «Завершить» |
| `bumped` | bool | запись вызвала бамп цикла |

Снимок `record_format` не даёт изменению упражнения исказить старую историю.
Если формат упражнения редактируется, прошлые записи сохраняют прежний формат.

### 8.2 `WorkoutSet`

| Поле | Тип | Назначение |
|---|---|---|
| `id`, timestamps | общие | |
| `entry_id` | FK → WorkoutEntry | |
| `position` | int | порядок |
| `weight_kg` | float? | вес, если предусмотрен форматом |
| `reps` | int? | повторения, если предусмотрены |
| `duration_sec` | int? | время |
| `distance_m` | float? | дистанция |
| `rir` | int? | 0 = отказ, 1..5 запас, 6 = 10+ |
| `planned` | bool | серый плановый подход, ещё не подтверждён |

Удалённые пользователем подходы исключаются из статистики. Плановые подходы также
не участвуют в статистике до подтверждения.

## 9. Шаблоны тренировок

Шаблон — это состав тренировки, а не прогрессия и не цикл.

### 9.1 `WorkoutTemplate`

| Поле | Тип | Назначение |
|---|---|---|
| `id`, `owner_id`, timestamps | общие | |
| `name` | str | пользовательское название |
| `description` | str? | описание |

### 9.2 `WorkoutTemplateItem`

| Поле | Тип | Назначение |
|---|---|---|
| `id`, timestamps | общие | |
| `template_id` | FK → WorkoutTemplate | |
| `exercise_id` | FK → Exercise | |
| `position` | int | порядок в тренировке |

### 9.3 `WorkoutTemplateSet` — опциональные плановые подходы

Поля те же, что у метрик `WorkoutSet`: `position`, `weight_kg`, `reps`,
`duration_sec`, `distance_m`, `rir`. Метрики проверяются по формату упражнения.

Применение шаблона к дате выполняется одной локальной транзакцией:

1. прочитать элементы в порядке `position`;
2. создать `WorkoutEntry` для каждого упражнения;
3. скопировать заданные подходы как `planned=True`;
4. сохранить `source_template_item_id`;
5. добавить изменения в Outbox только если синхронизация включена.

Шаблон не поддерживает связь с прошлым применением жёстко: после добавления
пользователь может свободно менять тренировку, не изменяя сам шаблон.

## 11. Локальные файлы

### 11.1 Структура на устройстве

Базовый путь получается через `path_provider`, а не задаётся абсолютной строкой.
Предпочтительна приватная папка Application Support; экспортируемые пользователем
файлы можно дополнительно сохранять через системный диалог.

```text
<ApplicationSupport>/WorkoutTracker/
├── workout_tracker.db          ← основная SQLite
├── media/
│   ├── exercises/<uuid>/...
│   └── templates/<uuid>/...
├── backups/
│   └── workout-backup-*.zip
├── exports/
│   ├── workout-export-*.json
│   └── workout-export-*.csv
└── tmp/                        ← незавершённые записи, очищается при запуске
```

Сама SQLite — тоже локальный файл. Сервер не нужен ни для базы, ни для медиа,
ни для экспорта.

### 11.2 `LocalFile` — метаданные файла

| Поле | Тип | Назначение |
|---|---|---|
| `id`, `owner_id`, timestamps | общие | |
| `entity_type` | str? | `exercise`, `template`, `backup` и т. п. |
| `entity_id` | UUID? | связанная сущность |
| `kind` | str | `image`, `import`, `export`, `backup` |
| `relative_path` | str | путь только относительно корня приложения |
| `mime_type` | str | тип содержимого |
| `size_bytes` | int | размер |
| `sha256` | str | проверка целостности и дедупликация |

Бинарные данные не хранятся в SQLite. В БД находятся только метаданные и относительный
путь. Абсолютные пути не синхронизируются и не переносятся между устройствами.

### 11.3 Правила `FileStorage`

- разрешать файлы только внутри корня приложения; запретить `..` и выход по symlink;
- записывать через временный файл, затем атомарно переименовывать;
- проверять расширение, MIME и размер изображения;
- удалять файл после удаления последней ссылки на него;
- периодически очищать `tmp` и файлы-сироты;
- не удалять исходный импорт до успешного завершения операции;
- при отсутствии места сохранять БД целой и показывать понятную ошибку.

Локальные медиа не отправляются на сервер автоматически. Удалённая синхронизация
файлов — отдельная опция на будущее, не требование для основной работы.

## 12. Резервные копии, экспорт и импорт

Для переносимости используется ZIP, а не копирование внутренней SQLite напрямую:

```text
workout-backup.zip
├── manifest.json
├── data.json
└── media/...
```

`manifest.json` содержит `backup_version`, версию приложения, дату создания и
контрольные суммы. `data.json` содержит все сущности в канонических единицах и с UUID.
Формат версионируется отдельно от версии SQLite.

Перед импортом приложение:

1. проверяет версию и контрольные суммы;
2. читает архив во временную папку;
3. валидирует данные и ссылки;
4. предлагает явный режим «заменить» или «объединить»;
5. автоматически создаёт backup текущего состояния;
6. применяет импорт транзакционно и только затем заменяет файлы.

Ошибочный импорт не должен оставлять половину новых данных. Экспорт CSV предназначен
для просмотра истории, а ZIP — для полного восстановления приложения.

## 13. Бизнес-логика и сервисы

Поскольку приложение работает офлайн, правила должны существовать и на Dart, и на
Python. Чтобы они не разошлись, формулы и примеры результатов оформляются как общие
JSON-fixtures и прогоняются тестами на обеих платформах.

### 13.1 Расчёты и единицы

```text
epley(weight, reps)       = weight * (1 + reps / 30)
round_down_to_step(v, s)  = floor(v / s) * s
kg ↔ lb
m ↔ km ↔ mi
seconds ↔ h:mm:ss
```

Для Эпли с RIR используется то же правило, что во Flutter-макете. Конвертация единиц
не участвует в формуле: все расчёты выполняются в канонических величинах.

### 13.2 `DiaryService`

- добавление упражнения отдельно, из цикла или из шаблона;
- копирование подходов цикла с `planned=True`;
- подтверждение и редактирование подхода по `RecordFormat`;
- завершение и отмена завершения;
- продвижение и откат цикла только при соблюдении правила более поздних записей;
- удаление записи и восстановление связанного состояния цикла;
- изменение порядка упражнений;
- мягкое удаление и исключение удалённого из статистики.

После последнего дня силового цикла: `tm_kg += step_kg`,
`weight_offset_kg += step_kg`, всем точным плановым весам добавляется `step_kg`,
`current_day = 0`. Операция выполняется в одной транзакции вместе с завершением записи.

### 13.3 `ExerciseService`

- фильтры по группе, мышце, формату и строке поиска;
- создание/редактирование пользовательского упражнения;
- управление переводами;
- назначение primary/secondary мышц;
- проверка обязательных полей формата;
- архивирование вместо удаления, если уже есть история.

### 13.4 `TemplateService`

- CRUD шаблонов и порядок упражнений;
- опциональные плановые подходы;
- атомарное применение к дате;
- независимость применённой тренировки от дальнейших изменений шаблона.

### 13.5 `StatsService`

Статистика выбирается по формату записи:

| Формат | Основные метрики |
|---|---|
| `WEIGHT_REPS` | расчётный 1ПМ, максимальный вес, тоннаж, максимум повторений |
| `WEIGHT_TIME` | максимальный вес, максимальное/суммарное время |
| `TIME_REPS` | максимум/сумма повторений, максимальное/суммарное время |
| `TIME_DISTANCE` | дистанция, время, темп и скорость |

Для каждого формата доступен свой набор графиков и плиток. Нельзя складывать тоннаж
бега и жима или вычислять Эпли по времени. Все запросы выполняются к локальной SQLite;
FastAPI повторяет их только для серверной копии.

## 15. Синхронизация без нарушения автономности

### 15.1 `OutboxOperation`

| Поле | Тип | Назначение |
|---|---|---|
| `id` | UUID | идемпотентность операции |
| `entity_type` | str | тип сущности |
| `entity_id` | UUID | объект изменения |
| `operation` | enum | upsert/delete |
| `payload_json` | str | снимок изменения |
| `created_at` | datetime UTC | порядок отправки |
| `retry_count` | int | число попыток |
| `last_error` | str? | диагностика |

`SyncState` хранит `sync_cursor`, `device_id`, время последней успешной синхронизации
и версию серверной схемы.

### 15.2 Алгоритм

1. Пользовательское действие записывается в локальную БД.
2. При включённой синхронизации в той же транзакции создаётся Outbox-запись.
3. UI сразу получает успешный результат.
4. При наличии сети SyncService отправляет пакет операций.
5. Сервер подтверждает принятые UUID операций и возвращает изменения после cursor.
6. Клиент применяет серверные изменения и только затем удаляет подтверждённый Outbox.
7. При ошибке локальные данные остаются; повтор выполняется позже с backoff.

Базовое разрешение конфликтов — last-write-wins по `updated_at`, с детерминированным
tie-breaker по `device_id` и `id`. Tombstone побеждает более старое обновление и не
удаляется до подтверждения всеми устройствами. Операции идемпотентны по UUID.

Для первой версии достаточно синхронизации целых сущностей. Если позже появится
одновременное редактирование одного упражнения на нескольких устройствах, добавляются
`revision` и ручной экран конфликтов — фундамент менять не потребуется.

## 16. Миграции и совместимость

### 16.1 Переход от текущего Flutter-снапшота

1. При первом запуске новой версии создать SQLite и миграции.
2. Прочитать текущий JSON-снапшот, не удаляя его.
3. Сгенерировать UUID и перенести упражнения, циклы и дневник.
4. Назначить старым упражнениям `WEIGHT_REPS`.
5. Перенести вес в `weight_kg`, повторения в `reps`, остальные метрики оставить null.
6. Создать русские переводы текущих названий.
7. Проверить количество записей и контрольные суммы.
8. Сделать backup и только затем пометить старый снапшот как мигрированный.

### 16.2 Серверные миграции

Alembic добавляет новые таблицы и колонки постепенно. Старые записи получают
`WEIGHT_REPS`; удаление старых колонок выполняется только после успешного backfill.
Локальные и серверные версии схемы независимы, но DTO имеют явную версию.

## 17. Тестирование

Обязательные группы тестов:

- формулы Эпли, RIR, округление и бамп цикла;
- конвертация кг/фунтов и метров/миль без изменения исходных данных;
- валидация всех четырёх форматов;
- создание упражнения с переводами и мышцами;
- применение шаблона и откат транзакции при ошибке;
- SQLite roundtrip и миграция текущего JSON;
- сохранение/чтение локального файла и запрет выхода за корень;
- полный backup → очистка тестовой БД → восстановление;
- работа основных сценариев с отключённой сетью;
- повторная отправка Outbox без дублирования;
- одинаковые расчёты Dart/Python на общих fixtures;
- тесты статистики, исключающие planned и удалённые записи.

## 18. Порядок реализации

1. **Локальная SQLite-схема и миграция снапшота.** Репозитории, UUID, нормализованные таблицы.
2. **Форматы и единицы.** Расширение моделей и редакторов подходов, кг/фунты.
3. **Каталог и локализация.** ARB, переводы упражнений, группы и мышцы, редактор упражнений.
4. **Шаблоны.** CRUD и применение к тренировочному дню.
5. **Локальные файлы и backup.** FileStorage, ZIP-экспорт/импорт, проверка целостности.
6. **Статистика форматов.** Отдельные метрики и графики.
7. **FastAPI.** Модели и endpoints по той же спецификации.
8. **Опциональная синхронизация.** Outbox, cursor, конфликты и тесты повторной отправки.

Такой порядок не делает мобильное приложение зависимым от сроков разработки бэкенда.

## 20. Что осознанно не входит в первую реализацию

- обязательная регистрация и облачный аккаунт;
- автоматическая загрузка медиа на сервер;
- одновременное совместное редактирование одной тренировки;
- отдельные стратегии циклов для кардио и временных упражнений;
- микросервисы, очереди сообщений и фоновые push-задачи.

При этом UUID, локальные файлы, Outbox, форматы записей и переводы уже заложены,
поэтому перечисленные возможности добавляются без смены фундамента.
